# 首屏直答卡选品协议（quickAnswers）

目标：**卡面即答案**——用户看完卡就能行动，点进正文是为加深理解，不是为拿到答案。本节协议来自 `docs/drug-card-set-v0.1.md`（活文档，以最新轮次实测为准）；该文档 §七（2026-09-16 的 6 卡）与页面现行 6 卡（决策链版）是两个已拍板版本，**新页面以 `src/content/drugs/osimertinib.md` 现行为参照实现**。

## 一、四道闸门 + 一道落点检查

「搜得多」只是必要条件。一张卡必须同时过前两道，③④ 决定排序：

| 闸门 | 判定问题 | 淘汰特征 |
|---|---|---|
| ① 终局性 | 卡面上能不能把事办完？不点正文也能行动？ | 答案是一份文件、一次匹配、多步操作（说明书原文、临床试验怎么参加） |
| ② 单一答案 | 答案是确定数字/规则/是非，还是「因人而异」？ | 答案只能由医生给——上卡面必然退化成免责声明（同类药哪个好、多久复查） |
| ③ 高频 | ≥3 个引擎命中，或 ≥10 槽位？ | 单引擎孤证、一句话可答的认知类常识（是几代靶向药→并入他卡补充句） |
| ④ 错答有代价 | 没看到正确答案会做危险动作吗？ | 无代价的科普 curiosity |

**第五道检查 · 落点唯一性**：两张卡落同一个锚点 = 用户看到的重复（悬停见同一 href、点击落同一屏）。N 张卡必须 N 个不同锚点。两问只能落一节时：拆节或并卡，禁止挤同一锚点。锚点不够用暴露的是正文颗粒度不足，不是卡面选错。

## 二、六卡预算与现行选型（决策链）

固定 6 张，顺序即患者决策链：**治什么 → 有没有效 → 多少钱 → 能报多少 → 去哪买 → 能不能换便宜的**。

| # | question（患者原话） | answer 形态 | anchor |
|---|---|---|---|
| 1 | 这个药能治哪些病？ | 一句话划线适用范围 | 哪些人适合用 |
| 2 | 能治好吗？生存期能延长多少？ | 是非 + 数字，「延长」主语是药不是人 | 疗效 |
| 3 | 一个月、一年要花多少？ | 具体金额 + 时间口径 | 要花多少钱 |
| 4 | 医保能报多少？ | 比例 + 参保类型拆分 | 医保能报多少 |
| 5 | 在哪里能买到？ | 关键限制/路径 | 在哪里能买到 |
| 6 | 仿制药能替代吗？ | 能/不能 + 前提 | 仿制药能替代吗 |

非肿瘤药等不适用药种：整条链按该药真实决策路径重排（如「这个药治什么病→吃多久→副作用→多少钱→医保→去哪买」），闸门与落点规则不变，**不要把「仿制药」硬塞给没有仿制的原研独占期品种**——选品永远重新过闸。

明确不上卡面（避免反复讨论）：同类药怎么选（答案归医生）、说明书原文（给不出文件）、临床试验怎么参加（只能给入口）、多久起效/多久复查（答案不收敛）、分子式/图片（全档案属性）、相互作用清单（是一张表不是一句话）。

## 三、字段与文案预算

六字段：`question / answer / detail / nextStep / source / anchor`。

- **question ≤ 约 14 字、单行不折**；用患者搜索原话（下拉词取证），但过语气检查（「能活多久」→「生存期能延长多少」）。一张卡只留一个疑问点。
- **answer 一句话结论，11–24 字**。这是体例：答案先给限制或关键事实（「处方药，自己买不到；医院还常缺药」「晚期不能根治，但…」）。**同一组卡内结论位置体例统一，逐字不改口头版**——历史上六条 answer 曾「逐字不动」整体保留，只压 detail。
- **detail 34–64 字**，只回答「为什么是这个结论」。操作细节、例外、数字折算一律撤到正文；**撤出前逐条核对正文有完整版本兜底，不许信息净损失**（这是当年压缩被批准的前提）。
- **nextStep**：一句「看××、××」指向正文该节会回答什么；与正文当前结构一致（正文把「四道坎表」改叙述后，nextStep 同步改过一版）。
- **source**：到字段级的出处（「甲磺酸奥希替尼片说明书（用法用量）」），是卡面唯一的日期/来源承载位。
- **anchor**：只填标题**前缀**（模板 `startsWith` 匹配 H2+H3）。风险：前缀不命中时模板**静默回落到目录第一项**，页面看不出坏了——所以校验脚本必须硬拦「anchor 解析不到对应标题」。

## 四、版式契约（模板已固化，内容侧不要逆着写）

- DOM 顺序：问题(18px) → 直接回答(17px 粗体) → 详细回答(15px，浅灰左竖线) → 「想看详细解释？」(14px 品牌色，与来源同底部容器) → 来源(13px)。无「问题」「直接回答」标签。
- 标题末尾加「？」不改变锚点 slug（slugger 去标点），但卡面 `anchor` 前缀必须与**改后**标题前缀一致。
- 桌面 6 卡 3 列等高；移动端卡约 247–289px 高，靠 detail 字数预算维持，不靠 CSS 截断。
- **枚举卡（填了 `options`）走另一套版式**：问题(17px) → 四格选项表（`grid-cols-2`＋1px 十字线外框，格内 15px 居中，2×2 等宽等高）→ 详细回答 → 引导 → 来源。这种卡**不渲染 `answer`**：一组选项本身就是答案，再写一句结论会和表格重复。`answer` 字段仍必填，供 FAQPage JSON-LD 拼成完整答案句（`{answer}：{options 顿号连接}`）。选项数取偶数（2 列成对，奇数会留半格空）。
- 选项卡的视觉形态**默认用四格表格，不用带底色描边的胶囊**：胶囊会把注意力从答案抢走，且换行时无法保证两列对齐（2026-10-08 定稿口径）。

## 五、与其他层的一致性

- 卡面数字 = 正文该节 = FAQ = `labelFacts` = numbers.json 同一值（见 source-hierarchy.md）。
- 同一页两张卡不复述同一个数字；数字只留在回答它的那张卡。
- FAQPage JSON-LD 收录卡面 6 条 + FAQ：去重只按完全同问，近义问句会并存——可接受，但同问句不要字面重复。
- 卡面选品有效期受 SERP 时间约束：下拉词是某天采集的，**隔了很久更新页面先重采再定卡**（审计曾发现 09-11 定的卡落后于 09-16 实拉共识词）。
